The core Git workflow has three zones. Every file moves through them in order.

📁
Working directory
Your project files on disk. Edit freely here.
git add
›
📋
Staging area
A waiting room. Chosen changes go here first.
git commit
›
📚
Repository
Permanent history. Every commit lives here forever.
Step-by-step: your first commit
1

Create a project folder

$ mkdir my-java-project && cd my-java-project
2

Initialize a Git repository

This creates a hidden .git folder — Git's brain. Never delete it.

$ git init
Initialized empty Git repository in /path/to/my-java-project/.git/
3

Check what Git sees

Run this often. It tells you exactly what state your files are in.

$ git status
On branch main
No commits yet

Untracked files:
(use "git add <file>..." to include)
HelloWorld.java
4

Stage your file

Move HelloWorld.java from the working directory into the staging area. Use git add . to stage everything at once.

$ git add HelloWorld.java
5

Commit — take a snapshot

The -m flag sets the message inline. Be descriptive.

$ git commit -m "Add HelloWorld.java"
[main (root-commit) abc1234] Add HelloWorld.java
1 file changed, 5 insertions(+)
6

View commit history

Use --oneline for a compact, readable log.

$ git log --oneline
abc1234 Add HelloWorld.java
The three file states

Every file in your project is always in one of these states:

Untracked
Git sees the file but isn't watching it yet
git add
›
Staged
Queued for the next commit
git commit
›
Committed
Saved permanently in the repo
Commands at a glance
CommandWhat it does
git initStart tracking a folder as a Git repository
git statusSee which files are untracked, modified, or staged
git add <file>Move a file into the staging area
git add .Stage all changed files at once
git add -pInteractively pick parts of a file to stage (cleaner commits)
git commit -m "…"Save staged changes as a snapshot with a message
git commit --amendRewrite the most recent commit message or content
git logView full commit history (author, date, message)
git log --onelineCompact one-line view of commit history
Writing good commit messages

Commit messages are a diary for your future self and teammates. Make them count.

AVOID
fix
update
changes
wip
Too vague. Says nothing about what changed or why.
PREFER
Add user login validation
Fix null pointer in UserDAO
Create User model with getters
Short, imperative, and specific. A future reader knows exactly what happened.
Best practices
🔁
Commit often
Small, frequent commits are easier to review and revert than one big commit at the end.
👁
Always check status first
Run git status before committing so you know exactly what's going in.
🚫
Use .gitignore
List files Git should never track: target/, .class, IDE folders, secrets.
🧩
One concern per commit
A bug fix and a new feature should be two separate commits, not one.
